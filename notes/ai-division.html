AIとの分業（研究ノート）

作成 2026-10-02　更新 2026-10-10

関連：試作で比べる進め方

1. やりたいこと

  • 個人開発（合コンゲーム『今夜のスタメン』）で、人とAIの役割分担をうまく回したい
    • きっかけは「うまく分業できていない感じがする」（10/2）
  • 10/10 に、知りたいことが増えた
    • 本業（システム開発）の実験としても使いたい
    • 今どんなレビューとテストをしているのか。あるべき姿と、その事例。Claudeの意見
    • 指示があいまいなので、安いモデル（Cursor の Composer など）を使えていないのではないか
    • トークン（利用量）を節約したいが、どこから手をつければいいか

2. 先行事例（要旨）

調査はサブエージェント（Sonnet）。URLは開いて確かめたものだけ。

誰・何 分け方 うまくいった／失敗
Grumbulus（親子）／素のJSのブラウザゲーム 約1.5万行 人は着想・試遊・感想、AIが設計から実装まで。仕様を固めず「遊ぶ→直す」を数分で回す 良：「弱い感じがする」型の感想が効く。失：機能を足すと図鑑・セーブの更新を忘れる、並列で作ったファイル同士の結合バグ
Lost Historia／C++の放置RPG（公開済み） UI＝Codex、実装＝Claude Code、素材＝別AI、画面の確認＝ローカルの画像AI。指示ファイルで「実装前に仕様を確認」を義務化 良：テストと画面確認でAIの「完了」を機械で検証。失：仕様が決まらないまま走って手戻り、予定より4か月遅れ
DungeonInn／Unityの経営シム Claude Codeが監督・設計、Codexが実装。人がレビューし、指摘を設計ガイドラインに残す 良：データの形を先に決めると後が楽。失：最初に単独で作らせたら負債化
kaedevn／ノベルゲーム制作の仕組み（人の手書きコード0行） ChatGPTで仕様書→Claude Codeが実装。仕様に「やらないこと」を書いて膨らませない 良：型と大量のテストで自走。懸念：全体を誰も把握していない
ソウルキャスターズ／長編ノベル プロット→評価→本文→実装→素材の発注書、の工程制。評価は別の会話のAIに第三者としてやらせる 良：別会話の評価が機能。失：設定の矛盾、指示が曖昧だと凡庸になる
Zapaleni RPG／ゲームBot（作者はコード未経験） 人＝設計とバランス判断、AI＝実装・公開・分析。プレイヤーの声をAIが要約→人が直す所を選ぶ→同日反映 良：試作2晩、6週で公開
7役サブエージェント構成／Webアプリ PM・設計・実装など7役を定義し、メインの会話をPM役に 失：多段の呼び出しや並列で文脈が膨らむ → 順番に回して解決

3. 調べたことと条件

共通の条件

  • 役割

    • 調べ物：サブエージェント（Sonnet）
    • 画像：Gemini／ChatGPT（ブラウザ）
    • 判断と試遊：ユーザー
  • 確認の場：スタメン確認ボード。項目ごとに「何を見るか」と、Claudeの返事が付く

調査1（10/2）：個人開発の分業事例

調査2（10/10）：レビューとテスト、安いモデル、トークン節約

  • サブエージェント（Sonnet）で、公式ガイド（Claude Code・Cursor・OpenAI Codex・GitHub Copilot）と記事・論文を調べた
  • あわせて、Claudeが今やっている確認の中身を書き出した（下の「今のやり方」）

4. 結果

調査1：共通して効いていること

  • 人は「面白さ・優先順位・やらないこと」を決める。実装はAI
  • 決めたことは会話ではなく文書に残し、仕様とコードを一緒に直す
  • 設計・実装・評価は別の会話（別のAI）に分け、評価は第三者にやらせる
  • 「完了」は機械で確かめる（テスト・画面の確認）
  • 並列は人がレビューできる数まで

今のやり方（10/10 時点）

  • レビュー：同じ会話のClaudeが、自分で見直しているだけ。別の会話・別のAIによるレビューはしていない
  • 構文の確認：書いたJavaScriptが読み込めるかを、毎回確かめる
  • 画面の自動テスト（tools/test_night_i.js）
    • Playwright（ヘッドレスのChromium）で、スマホ幅（390×780）のまま最後まで自動で遊ぶ
    • 待ち時間は6倍速にしている
    • 遊び方は5通り（ふつう／喋り続ける／黙り続ける／あおい狙い／話を遮る）。これを設定A・B・Cで回す
    • 画面に出ている吹き出し・札・話題・選択肢を読み、遊び方の決まりに従って押す
    • 要所でスクショを撮り、会話のログを保存する。ページでエラーが出たら失敗にする
    • スクショはClaudeが画像として見る。画面が横にはみ出していないか（ページの幅）も数字で見る
  • テストはファイルとして残してあり、直すたびに回している
  • していないこと
    • 受け入れ条件（どうなれば完了か）を、作る前に書くこと
    • 計算（好感度など）の単体テスト
    • 意地悪テスト（でたらめな連打・長押し・途中で戻る・でたらめな選び方）
    • 長時間プレイ（メモリが増え続けないか）と、遅い端末の再現
    • 別の会話でのレビュー

調査2：あるべき姿（公式ガイドと事例）

  • 確かめる手段を渡すのが最重要（Claude Code の公式）。テストやスクショの比較を渡し、入出力の例で受け入れ条件を書かせる[1]
  • レビューは別の文脈で。サブエージェントか別の会話に見せ、指摘は「正しさと要件」に絞る。絞らないと作り込みすぎになる[1]
  • テストを先に。テストを書かせて失敗を確かめ、「テストを変えずに」通させる（Cursor）[2]
  • 依頼の書き方：目的・文脈・制約・完了条件を書く（OpenAI Codex）[3]。課題文に受け入れ条件と対象ファイルを書く（GitHub Copilot）[4]
  • 実際に動かして見る：テストが通っても起動で落ちることがある。Playwrightで動かしてスクショを見る。見つけた不具合は、失敗するテストにしてから直す[5]
  • 意地悪テスト
    • gremlins.js：でたらめなクリック・入力・スクロールを送る。乱数の種で再現でき、フレーム落ちとエラーも拾う[6]
    • fast-check：性質（「どの選び方でも詰まらない」など）を決めて、たくさんの入力で確かめる。失敗した入力を小さく縮めてくれる[7]
  • 負荷テストの代わり（サーバーが無い静的サイトなので、負荷そのものは要らない）
    • ソーク試験：同じ操作を200回くり返し、画面の部品の数やイベントの数が増え続けないかを見る[8]
    • 遅い端末：ChromiumでCPUを遅くして遊ぶ[9]。スマホの画面は Playwright の端末エミュレーションで[10]
  • 安いモデル
    • Cursor の Composer 2.5（5/18）は、100万トークンあたり入力0.5ドル・出力2.5ドル。Cursor のアプリの中で使うモデル[11]
    • Claude側の目安は、ふだんの作業は Sonnet、設計や難問は Opus。サブエージェントには Haiku も指定できる[12]
    • 「あいまいな問題や難問は大きいモデル、決まった作業は小さいモデル」という推奨がある[13]
    • 研究では、モデルは「仕様が足りないか」の判断が苦手で、質問させると最大74%よくなった[14]
  • トークンの費用：文脈の量に比例する。キャッシュから読むぶんは入力の0.1倍、出力は入力の約5倍。途中でモデルを変えるとキャッシュが捨てられる[13][15]。常駐の指示ファイルを足すと、成功率は上がらずに費用が20%以上増えたという研究もある[16]

5. 分析

うまくいっていること

  • 調べ物をサブエージェント（Sonnet）に任せる分け方は回っている。10/10 の3件の調査もこれ
  • 画面の自動テストが「最後まで通るか」を毎回機械で確かめていて、事例の「完了は機械で確かめる」に合っている
  • 確認ボードの「何を見るか」は、受け入れ条件の手前まで来ている

足りないこと（本業の工程に当てはめると）

工程 今 足りないこと 次の一手
要件・受け入れ条件 ボードの「何を見るか」 作る前に合否の条件がない 依頼1つに「どうなれば完了か」を1行書く（Claudeが書いて、あなたがOKする形でもよい）
製造 Claudeが実装 — —
単体テスト なし 好感度の計算などを数字で確かめていない 計算の部分だけ、小さな試験を足す
画面テスト（結合） 自動プレイ5通り×3設定、スクショ 見ているのが作った本人（同じAI） 大きい変更のときだけ、別の会話に「正しさと要件」だけ見せる
意地悪テスト なし 連打・長押し・途中で戻る・でたらめな選び方 でたらめな遊び方を50通り回し、「詰まらない・エラーが出ない」を確かめる
負荷テスト なし 負荷は不要。代わりに長時間と遅い端末 12/6の試遊会の前に1回だけ：200回くり返して部品の数を見る、CPUを4倍遅くして遊ぶ
レビュー 自己レビュー 第三者の目 上の「別の会話」と同じ

安いモデルについて（質問への答え）

  • 半分あたり。原因は「指示のあいまいさ」そのものより、「合否を判定できるもの（受け入れ条件とテスト）がないこと」
    • あいまいな依頼は、高いモデルでも手戻りになって費用が増える
    • 合否がテストで決まる作業なら、安いモデルでも任せやすい
  • 任せやすい作業：範囲が狭い、仕様がはっきりしている、テストで正否が出る
    • このプロジェクトなら：調べ物、決まった形への書き換え（例：読みものの構成をそろえる）、テストを足す、移植
  • 任せにくい作業：台詞の質、見た目、設計の判断。テストで測れないもの
  • Composer を使うなら Cursor に移る必要がある。今の環境（Claude）での「安いモデル」は、Sonnet や Haiku のサブエージェント

トークン節約：どこから手をつけるか（効く順）

  1. 会話を分ける（1テーマ1会話）。この会話は何日も続いていて、毎回とても長い文脈を読み直している。いちばん効く - 例：絵（立ち絵・表情）／会話の仕組み／ポートフォリオ／ボードと計画 - 引き継ぎは、研究ノートと確認ボードがあるので困らない
  2. 受け入れ条件とテストで手戻りを減らす。手戻りは一番高い
  3. 調べ物と決まった作業はサブエージェント（Sonnet）へ。メインの会話には結論だけ返させる
  4. 画面の確認は、スクショを小さくまとめて見る。画像は文脈を大きく使う
  5. 常駐の指示（CLAUDE.md など）は短く。手順はスキルへ移す
  6. モデルの使い分けは最後。途中で変えるとキャッシュが捨てられるので、会話の頭で決める

Claudeの意見

  • 本業の実験として一番効くのは、「受け入れ条件を1行書く → テストで確かめる → 別の会話でレビュー」の型を1回やってみること。工程表を全部まねるより、この3つで足りる
  • 意地悪テストは、このゲームでは費用に見合う。会話が自動で流れ、時間制限と長押しがあるので、「押す時機がずれたら詰まる」種類の不具合が出やすい
  • 負荷テストは、今は要らない。公開前に長時間と遅い端末を1回見れば十分
  • 正直に言うと、今いちばんトークンを使っているのは、この会話が長すぎること。次の週末から、テーマごとに会話を分けるのを勧める
